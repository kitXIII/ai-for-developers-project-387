# Деплой на Render: Docker-образ из репозитория, Blueprint и free-план

Status: accepted

Прод проекта 387 — сервис `kit-calls-calendar` на Render (<https://kit-calls-calendar.onrender.com>):
Render собирает образ из `Dockerfile` в этом репозитории и деплоит его из `main` на каждый коммит,
а инфраструктура описана `render.yaml` и применяется Blueprint. Прод проекта 386 — отдельный сервис
`kit-calls` (<https://kit-calls.onrender.com>); он остаётся живым и этим решением не управляется.
Решение собрано по итогам карты «Деплой на Render: Docker-сервис, Blueprint и автодеплой из main»
([#38](https://github.com/kitXIII/ai-for-developers-project-386/issues/38), проект 386) и резолюций
её тикетов.

## Контекст

Приложение — один процесс Fastify 5 с `@fastify/vite`: он отдаёт и API, и SPA, поэтому `/` и `/admin`
должны отвечать с одного origin, а состояние живёт в памяти процесса. Нужен публичный прод без ручного
администрирования, без секретов в репозитории и без бюджета: проект учебный.

Проект 387 — продолжение 386, но прод первого проекта остаётся на своём сервисе: копия получает
собственный инстанс, чтобы работа над 387 не меняла то, что уже выкачено у 386. Отсюда два независимых
сервиса с одинаковым приложением и разными репозиториями-источниками; общими у них остаются только
free-план и регион.

## Решение

**Render, `runtime: docker`, сборка из репозитория.** Сервис — `type: web`, имя `kit-calls-calendar`,
ветка `main`, `dockerfilePath: ./Dockerfile`, контекст `.`. Образ собирает Render на своей стороне:
registry, теги образов и права на пуш не нужны. `Dockerfile` — тот же multi-stage, что и для локального
`mise run docker:build` (клиент и сервер в `dist/`, прод-зависимости, `USER node`), поэтому прод-артефакт
совпадает с контейнером, который поднимается локально.

**Деплой на каждый коммит в `main`: `autoDeployTrigger: commit`.** В `main` можно попасть только через
мерж PR — это держит ruleset репозитория, — поэтому `commit` и означает «деплой после мержа».
`checksPass` отвергнут: в этом режиме Render ждёт **все** чеки коммита, включая внешний `hexlet-check`,
который запускается вне наших workflow. Его отсутствие или краснота блокировали бы поставку, а гейт
качества должен жить на этапе мержа, а не выкатки. Гейт перенесён в ruleset: PR не смержить без зелёных
`Quality gates`, `Docker build` и `Architecture gate`. `Docker build` собирает тот же `Dockerfile` до
мержа, поэтому сломанный образ не попадёт в `main`, а Render затем собирает его же из `main`.

**Health check — `/`.** `healthCheckPath: /` отдаёт SPA-индекс, а значит проверяет и сборку клиентского
бандла, и `@fastify/vite`, а не только живость процесса. API при приёмке проверяется отдельно:
`GET /api/v1/meeting-types`.

**Инфраструктура — Blueprint из `render.yaml`.** Сервис создаётся и меняется через Render MCP:
`create_blueprint` → `plan_blueprint` → `approve_blueprint`. Файл читается из удалённого репозитория,
поэтому правка должна быть в `main` до планирования. `render.yaml` — источник правды, дашборд — только
просмотр. `existingResources: create_new`: сервис `kit-calls-calendar` новый, поэтому суффикс к имени
не добавляется, а существующий `kit-calls` проекта 386 не затрагивается.

**Free-план, регион singapore.** `plan: free` указан явно: в схеме Blueprint дефолт платный. Имя
`kit-calls-calendar` на `onrender.com` было свободно.

**Два инстанса, один код.** `kit-calls` (проект 386) и `kit-calls-calendar` (проект 387) — разные
сервисы с разными репозиториями-источниками. Правки в 387 не деплоятся в 386 и наоборот; переключение
старого сервиса на новый репозиторий не делаем, чтобы не сломать прод первого проекта.

## Considered options

- **`checksPass` (как у `kit-calls` проекта 386)**: деплой только после зелёных чеков. Отвергнуто:
  Render ждёт все чеки коммита, включая внешний `hexlet-check`; его отсутствие останавливает выкатку.
  Качество важнее проверять до мержа, а не после него.
- **Переключить существующий `kit-calls` на репозиторий 387**: отвергнуто — это прод 386, переключение
  смешало бы истории проектов и потребовало бы правки Blueprint первого проекта. Новый инстанс дешевле
  и не трогает работающий прод.
- **Registry + image-based сервис**: собирать образ в GitHub Actions, пушить в GHCR и отдавать Render
  готовый образ. Отвергнуто: Render собирает из репозитория без дополнительных прав и кешей, а деплой
  готовых образов MCP не поддерживает, так что путь добавил бы лишние звенья (пуш, теги, второй кеш) и
  не упростил бы ни выкатку, ни откат.
- **Native Node runtime**: Render ставит зависимости и запускает `pnpm build` сам. Отвергнуто: прод
  собирался бы не тем `Dockerfile`, который проверяется локально и в job `Docker build`, — окружения
  разъехались бы, а паритет «локально = CI = прод» и был причиной завести Docker.
- **Платный план**: убирает засыпание и даёт больше памяти. Отвергнуто: для учебного проекта цена не
  оправдана, а засыпание и пустые данные после рестарта приняты осознанно (см. «Последствия»).
- **Ручной деплой из дашборда вместо автодеплоя**: отвергнуто: `commit` делает пуш в `main`
  единственным действием, а `trigger_deploy` остаётся обходным путём для пересборки без коммита.

## Последствия

- Данные не переживают рестарт: засыпание free-плана, деплой и падение процесса стирают in-memory
  хранилище. При `commit` рестарт происходит на каждый мерж в `main` — включая мерж релизного PR от
  release-please, который не меняет код. Для демо это приемлемо, keep-alive пингер не заводим.
- Первый запрос после простоя ждёт холодного старта.
- Гейт качества — ruleset на мерже, а не Render. Если смержить в обход правил (bypass роли admin),
  сломанный коммит выкатится сразу; при обычном потоке это невозможно.
- Blueprint — public alpha: после первого sync его `status` может остаться `error`, хотя
  `plan_blueprint` отдаёт `no_changes`. Источник правды — план, а не статус; поведение разбирается в
  [#46](https://github.com/kitXIII/ai-for-developers-project-386/issues/46) (проект 386).
- Порт приходит из `PORT`: `Dockerfile` слушает `$PORT`, поэтому локально это 3000, а на Render —
  значение платформы.
- Два free-сервиса делят часы free-плана workspace: `kit-calls` и `kit-calls-calendar` могут влиять
  друг на друга по бюджету, хотя спят после простоя и в сумме редко выбирают лимит.
- Сборка образа в CI — отдельный job, а не `mise run check`: быстрый локальный гейт сохраняется, но
  красная сборка видна только после пуша.

## Вне рамок

PR-preview окружения, кастомный домен и TLS, персистентное хранилище, keep-alive пингер против
засыпания и любые секреты или переменные окружения, кроме локального `RENDER_API_KEY` для MCP.
